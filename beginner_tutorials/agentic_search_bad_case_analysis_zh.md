# Agentic Search Bad Case 分析入门

## 1. Bad Case 分析是什么

Bad Case 是模型表现不符合预期的样本，例如：

- 最终答案错误；
- 答案正确但奖励为 0；
- 答案错误却得到高奖励；
- 没有调用搜索工具；
- 搜索很多次仍无法回答；
- 同一道题的所有 GRPO 候选奖励都相同。

分析 Bad Case 不是只记录“答错了”，而是回答三个问题：

1. 错误最早出现在哪个环节？
2. 这是偶发错误还是一类系统性错误？
3. 应该修改数据、搜索、Agent、奖励，还是训练配置？

## 2. 按完整链路定位错误

建议从前往后检查：

```text
原始数据
→ Prompt
→ 是否正确调用工具
→ Search Query 是否合理
→ 搜索服务是否正常
→ 返回资料是否包含答案
→ 模型是否正确使用证据
→ 最终答案与格式是否正确
→ 奖励是否正确反映质量
```

找到第一个出错点后，优先修复它。不要看到 reward 低就直接修改学习率、batch size 或训练步数。

## 3. 一个具体例子

问题：

```text
2024 年奥运会男子 100 米冠军是谁？
```

模型轨迹：

```text
搜索：2024 Olympic 100m winner
返回：混合包含男子、女子比赛和历届冠军
模型：没有继续核实
最终答案：Sha'Carri Richardson
奖励：0
```

逐层判断：

| 环节 | 结果 |
|---|---|
| 数据与标准答案 | 正确 |
| 是否搜索 | 已搜索 |
| Query | 缺少 `men's` 限定词 |
| 搜索结果 | 混入女子比赛信息 |
| 证据选择 | 选择了错误证据 |
| 多轮策略 | 没有二次核实 |
| 输出格式 | 正确 |
| 奖励 | 正确给出 0 分 |

根因是“查询生成不准确，并且缺少证据核实”，不是训练器或答案格式问题。

可尝试：

- 要求 Query 保留时间、主体、性别等限定信息；
- 发现冲突证据时继续搜索；
- 改进检索或增加 reranker；
- 加入证据一致性检查。

## 4. 常见类型与调整方向

### 4.1 答案错误，奖励也是 0

先判断正确资料是否已经出现在工具返回结果中：

- 没出现：调整 Query、索引、召回、top-k 或 reranker；
- 已出现但模型用错：调整 prompt、推理流程、模型基座或增加核实步骤；
- 任务普遍超出模型能力：考虑更强的 Instruct 模型或先做工具调用 SFT。

### 4.2 答案正确，奖励却是 0

例如模型输出“最终答案是 72”，奖励函数只接受 `#### 72`。

优先检查：

- 输出格式是否与答案提取规则一致；
- reward parser 是否过于严格；
- 标准答案类型是否一致；
- 答案正确奖励和格式奖励是否被混在一起。

这通常是格式或奖励问题，不是模型知识能力问题。

### 4.3 答案错误，奖励却是 1

这通常意味着奖励漏洞。例如模型只是在长文本中偶然出现标准答案，substring matching 就给了满分。

应当：

- 严格抽取最终答案；
- 检查答案标签数量和位置；
- 验证引用证据是否支持结论；
- 避免只用简单关键词包含关系评分。

### 4.4 模型不调用搜索工具

可能原因：

- prompt 没有说明何时搜索；
- 模型工具调用能力不足；
- chat template、tool schema 与 parser 不匹配；
- 不搜索也能依靠记忆得到奖励。

先检查工具调用格式和 parser，再考虑 prompt、少量 SFT 或更强的模型。不要简单强制所有问题都搜索。

### 4.5 搜索次数很多但效果不好

可能原因包括 Query 重复、不会判断证据是否充分、没有停止策略或搜索没有成本。

可调整：

- 限制最大搜索轮数；
- 对重复 Query 去重；
- 加入适度的搜索成本；
- 让 Agent 在每轮后判断证据是否充分。

### 4.6 GRPO 组内奖励完全相同

例如同一道题的 4 条轨迹都是：

```text
[0, 0, 0, 0]
```

此时组相对 advantage 基本为 0，这组样本难以提供有效更新。

可检查：

- 奖励是否过于严格；
- 输出格式是否导致统一得 0 分；
- 模型是否太弱；
- 采样是否缺乏多样性；
- 是否需要合理的部分奖励。

`mixed_groups` 表示组内同时存在不同奖励，是判断 GRPO 是否获得有效相对信号的重要指标，但不代表模型已经收敛。

## 5. 根因与修改位置对照表

| 根因 | 优先修改 |
|---|---|
| 问题、答案或标注错误 | 数据清洗与标注 |
| 模型不知道如何使用工具 | Prompt、SFT、模型基座 |
| Query 质量差 | 查询生成策略、Agent Loop |
| 搜索不到正确资料 | 索引、召回、top-k、reranker |
| 有证据但不会使用 | 模型能力、证据组织、推理流程 |
| 正确答案得 0 分 | 输出格式、答案抽取、奖励函数 |
| 错误答案得高分 | 修复奖励漏洞 |
| 搜索过多 | 停止策略、去重、成本惩罚 |
| GRPO 全组同分 | 采样、模型能力、奖励密度 |
| OOM、超时、worker 退出 | 工程配置与基础设施 |

## 6. 推荐分析流程

1. 从验证集或 rollout 中收集 Bad Case；
2. 按错误现象分类，而不是逐条随意阅读；
3. 每类选择 5～20 个代表样本；
4. 找到错误最早出现的环节；
5. 提出只改变一个因素的修复方案；
6. 在固定小集合上做修改前后对照；
7. 指标和人工轨迹检查都通过后，再扩大实验。

不要同时修改 prompt、检索、奖励和训练参数，否则即使结果提高，也无法判断真正有效的改动。

```markdown

- 样本 ID：
- 实验版本：
- 问题类型：
- 最终奖励：

### 现象

模型出现了什么问题？

### 轨迹摘要

- Query：
- 搜索结果：
- 最终答案：
- 标准答案：

### 最早错误点

数据 / Prompt / 工具调用 / Query / 检索 / 证据使用 / 输出格式 / 奖励

### 根因判断

为什么认为这里是根因？列出对应轨迹证据。

### 修改方案

只写本轮准备修改的一个变量。

### 验证方法

- 固定样本集合：
- 对照组：
- 主要指标：
- 成功标准：

### 结果

修改后是否改善？是否引入新的失败类型？
```

## 8. 核心原则

Bad Case 分析的目的不是为单个错误找理由，而是发现一类可以被统一修复的错误模式：

```text
现象 → 最早错误点 → 根因假设 → 单变量修改 → 对照验证
```
